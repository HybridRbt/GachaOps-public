# 旧助手登记与新版默认组合的衔接调查

日期：2026-11-24。状态：调查完成，未发现读写缺陷。来源：[GitHub #4](https://github.com/HybridRbt/GachaOps-public/issues/4)（历史 HYB-118），衔接[助手全局登记设计](助手全局登记设计.md)。

## 结论

“默认组合只有一条登记、其余待接入”是组合选择的正常结果，不是丢数据：旧版把接入路径存在每个组合里，升级后启动闸门只迁移数据目录内的旧组合文件，**数据目录外的旧配置文件不会被自动扫描**（设计如此）。旧文件里的其余登记通过「导入 → 预览 → 确认」进入全局登记即可恢复；旧文件保持原样，导入不改变它。

## 复现方法

```bash
python scripts/repro_registry_link.py --all --out issue4-results.json
```

脚本用临时目录与 `<sample>` 安装路径构造合成数据，逐场景以真实桌面入口离线运行（Qt offscreen，`QProcess.start` 被拒绝并计数，全程零启动）。结果 JSON 中真实路径已掩码为 `<data-root>`/`<sample>`。运行不触真实数据、不启动游戏。

## 场景与结果

| 场景 | 初始状态 | 操作 | 结果 |
| --- | --- | --- | --- |
| R1 | 旧组合：七项登记 | 普通启动 → 迁移确认 | 全局登记 7/7；组合转运行字段（顺序/勾选/超时/repeat_limit 保留）；选中组合不变 |
| R2 | 默认组合仅 1 项登记 + 目录外旧七登记文件（即 #4 观察态） | 普通启动迁移，再「导入」 | 迁移后登记 1 项；导入预览显示 ok-ww 冲突、6 项新增；冲突选“使用导入路径”→ 确认后登记 7 项、新建组合；**取消则零写入** |
| R3 | 就绪根 | `--config` 指向旧配置 | 草稿只带运行字段（登记路径不沿用，界面有提示）；保存为新组合，全局登记零改动 |
| R4 | 旧组合 | 迁移对话框选“取消并退出” | 程序退出，被跟踪文件逐字节零写入 |
| R5 | 两个组合对 ok-ww 有不同路径；zzz 仅目录无游戏 EXE | 启动迁移，冲突选候选 1 | 冲突候选要求显式选择；不完整候选自动延后待接入，不阻断迁移 |
| R6 | R1 之后 | 新建组合、重开程序 | 登记库对全部组合生效；重开后登记与组合均在，启动默认选创建最早的组合 |

## 对 #4 场景的恢复步骤

1. 用同一个数据目录打开新版 GachaOps，启动提示迁移时确认（只会收编数据目录内旧组合的登记）。
2. 「导入」选择升级前的旧配置文件 → 核对预览（哪些“新增”、哪些与当前登记冲突）。
3. 对冲突项选择保留当前值或使用导入路径 →「确认导入」。旧文件不会被修改；确认后核对全局登记数与各组合勾选、顺序、超时。
4. 每个组合共用同一份全局登记；切换组合不需要重新接入。

## 判定与边界

- 判定：#4 观察态属正常组合选择行为叠加指引缺口——迁移对话框只收编数据目录内的旧组合，不提示“目录外旧文件仍含登记”，需要用户主动导入。是否在迁移确认框补充一句指引属产品决定，非缺陷修复。
- 未发现读写缺陷：迁移、导入、取消、失败路径的写入范围与设计一致（失败回归见 tests/test_registration_migration.py、tests/test_registry.py）。
- 遗留实机项：真实安装目录下的接入检查（版本/原生设置）只影响“已接入，需处理”显示，不影响本调查的登记衔接结论，不在合成复现范围内。
